# 更新说明 v1.5.1

> 修的是「**开过微信提醒、以前能收到，这两天突然收不到**」这类查不动的问题。
> 这一版**动了后端**（`service.py` / `main.py`），**必须重启服务**才生效。

---

## 先说排查结论

我把整条推送链路用真实代码跑了一遍（`_verify/verify_notify.py`，**23 项全过**）：

- 有 SendKey 的账号，签到成功 → **确实会推**
- 同一天重复跑 → 正确去重，不轰炸
- 换到第二天 → 会重新推
- 签到报错 → 会推「失败」通知

**也就是说：发送逻辑本身没坏。** 坏的是「**失败被悄悄吞掉了**」：

| 以前的行为 | 后果 |
|---|---|
| 推送失败 → 只写服务器日志 `data/app.log` 里一行 warning | 控制台「日志」页干干净净，你完全看不出异常 |
| 账号没配 SendKey → 直接 `return`，一个字都不记 | 你只能听用户说「我没收到」，无从判断是他没开提醒还是推送挂了 |
| Server酱 返回的错误码（如「错误的Key」）只进了 warning | 到底是 Key 失效、超额、取关，还是网络问题，分不清 |

所以真正的毛病不是「不发」，而是「**不发也不告诉你为什么**」。

---

## 改了什么

### 1. 推送失败 → 原因写进控制台日志

`push_serverchan()` 改成 `push_serverchan_ex()`，返回 `(是否成功, 失败原因)`，
失败时把 Server 酱 的原始返回记进日志表：

```
checkin|推送失败：Server 酱：[AUTH]错误的Key
checkin|推送失败：Server 酱返回 HTTP 502
checkin|推送失败：网络错误：HTTPSConnectionPool(...) Read timed out
```

在控制台「日志」页直接能看到，不用再翻服务器文件。

### 2. 没配 SendKey 的账号也留痕（每天一条，不刷屏）

```
跳过|账号没配微信提醒（SendKey），这条消息没发
```

这样你能一眼分清「他根本没开提醒」还是「开了但推不出去」。

### 3. 设置页新增「🔍 用户微信提醒自检」

一键跑完所有账号，逐个试推一条，结果按账号列出：

| 状态 | 含义 |
|---|---|
| ✅ 正常 | 这条真发出去了，他去微信能看到 |
| ❌ 发不出去 | 推了但被 Server酱 拒了，后面跟着原因 |
| ⏸ 没开提醒 | 这个账号压根没填 SendKey，**永远收不到** |

「发不出去」的常见原因：SendKey 失效（`[AUTH]错误的Key`）、当天超了 Server酱 免费额度、
用户取关了「Server酱」公众号、服务器出网被挡。

### 4. 账号行新增「补发通知」按钮

发现某个用户没收到，点一下立刻补发一条「今天的签到情况」到他微信，
不用等到明天 —— 顺便验证这个人的 SendKey 还好不好使。
没配 SendKey 的账号显示为「未开提醒」（灰的，点不动），不会假装成功。

### 5. 用户自己开启提醒时，失败会显示真实原因

以前统一提示「请确认已关注公众号、SendKey 是否完整」，
现在是 `SendKey 已保存，但测试消息没发出去（Server 酱：[AUTH]错误的Key）。…`

## 升级方法

1. 覆盖 `app/service.py`、`app/main.py`、`app/static/index.html`、`app/config.py`、`app/__init__.py`
2. **重启服务**（这次必须重启：`service.py` / `main.py` 是后端代码）

```bash
# 宝塔「网站 → Python 项目 → 找到这个项目 → 重启」
# 或者终端里（一行就够）：
pkill -f run.py; sleep 1; cd /www/wwwroot/workbuddy-checkin && nohup python3 run.py >>data/run.log 2>&1 &
```

3. 浏览器 `Ctrl + F5` 打开控制台

### 升级后先做这一步（30 秒定位真凶）

控制台 →「设置」→ 结果通知那一片 →**「🔍 用户微信提醒自检」**。

- 全是 ✅ 正常 → 那几天是 Server酱 临时故障 / 网络抖动，现在已经恢复；
  让用户翻一下微信，或直接点账号行的「补发通知」补一条。
- 有 ❌ 发不出去 → 后面写的原因就是答案：
  - `[AUTH]错误的Key` → 这个用户的 SendKey 失效了，让他去 `/me` 重填一次
  - `Server 酱返回 HTTP 4xx/5xx` → Server酱 侧的问题，隔天再看
  - `网络错误` → 服务器出网问题（如果你在设置里填过代理，检查代理是否还活着）
- 有 ⏸ 没开提醒 → 这些人本来就不会收到，让他们去 `/me` 开一次

### 不想升级也能先查

服务器文件管理器打开 `/www/wwwroot/workbuddy-checkin/data/app.log`，
搜 `Server 酱` —— 里面早就有每次推送失败的原始原因了，只是以前没摆到台面上。

## 一个坑要注意

`logs` 表的 `message` 字段在成功时存的是话题名（`checkin` / `login`），
"今天是否已推送" 就是靠它去重的。所以**失败日志的 message 绝不能等于话题名**，
否则会被误判成「今天已经发过了」，把后面的重试全挡掉。
本版失败日志统一写成 `checkin|推送失败：…` 这种带前缀的形式，就是为了避开这个坑。
