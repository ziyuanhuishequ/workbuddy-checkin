## 一、每登录一次 +100 积分（已修）

### 你看到的现象

- 今天已经签到的账号，**每次扫码登录 → 「今日获得」又加 100**
- 跟账户里的真实积分对不上
- 每次都提示「签到成功」，而不是「今日已签到」

### 真正的原因（两个 bug 叠加）

**1. 上游的签到接口并不是幂等的**

我们原来信了「签到接口重复调用安全」这个假设，所以每次扫码成功都顺手调一次
`POST /v2/billing/meter/daily-checkin`。实际上：同一个账号重扫登录后，它**还会再返回一次成功并再发一次积分**。
而且「今天签没签」这个标志位在响应里的字段名并不固定（`today_checked_in` / `todayCheckedIn` / `checked_in`…），
原来只认一个名字，名字一对不上就被当成「今天还没签」→ 又去领一次。

**2. 本地把「每日额度」当成了「今天赚到的」**

「今日已签到」那条结果里带的是**每日签到额度**（100），我们把它也写进了签到日志的 `credit` 字段。
页面的「今日获得」是把这个字段求和的 —— 于是每登录一次就涨 100，账户里其实一分没多。

### 怎么修的

| 改动 | 位置 | 说明 |
|---|---|---|
| 新增 `checkin_marks` 表 | `db.py` | 按 **`uid + 日期`** 记账。只要这天真领过，当天就不再调领取接口 |
| 签到前先查标记 | `service.checkin_account` | 有标记 → 直接返回「今日已签到」，**完全不碰上游** |
| 签成功立刻记账 | 同上 | `claimed=True` 才写标记，并记下实际到账的积分 |
| 只记真到账的积分 | 同上 | 日志 `credit` 只在 `claimed=True` 时写，虚增消失 |
| 「今日已签到」不写签到日志 | 同上 | 免得「累计签到次数」被重复登录灌水 |
| 标志位兼容多种写法 | `wb._flag()` | snake / camel / 数字 / 字符串 / 嵌套一层，都能认 |
| 标记表定期清理 | `scheduler._prune_pass` | 只留最近 60 天 |

> 🔑 关键点：标记是按 **uid** 记的，不是按账号行记的。
> 所以你**删掉账号再重新扫码加回来**，当天也不会再领一次 —— 你反馈的场景正是这一种。

### 修完后的表现

- 今天第一次登录 → 真签一次，通知里写「今日签到：+100 积分（本次已到账）」
- 今天再登录（包括删号重加）→ 提示「**今日已签到**」，通知里写「今日签到：今日已签到，本次未新增」，**不动积分**

## 二、扫码登录为什么一直失败（查清了）

### 结论先说

**手机在微信里扫码，永远登不上。** 这不是软件的问题，是官方登录页自己把微信用户挡在门外了。

### 证据

把官方登录页（`https://copilot.tencent.com/login?platform=CLI&state=...`，会 302 到 `www.codebuddy.cn/login/`）
的 HTML 抓下来，里面有一段内联脚本，逻辑是：

```js
var ua = navigator.userAgent.toLowerCase();
var isWeixin = ua.indexOf('micromessenger') !== -1 && ua.indexOf('wxwork') === -1;
if (!isWeixin) { return; }          // 电脑浏览器：正常显示二维码

// 以下只对「微信内置浏览器」生效
// ⚠️【微信内网员工探测 · 总开关】
window.location.replace(
  'https://open.weixin.qq.com/connect/oauth2/authorize?appid=wxf3055eea2dff6d9c&...&scope=snsapi_base#wechat_redirect'
);
```

也就是说：**只要 UA 里带 `MicroMessenger`，页面立刻跳去一个「内网员工探测」的微信授权地址**，
用的是官方内部员工公众号 `wxf3055eea2dff6d9c`。普通用户不在那个公众号的服务范围内，授权过不去，
表现出来就是「登录失败 / 请返回客户端重新发起」。

同一个页面用**电脑浏览器**打开时，这段脚本直接 `return`，正常渲染登录二维码 ——
所以「电脑打开链接 → 微信扫屏上的码」是通的（你实测的结果完全对得上）。

### 结论：这不是我们能在客户端修掉的

二维码里装的就是那个 `authUrl`。手机微信扫它 → 必定用微信内置浏览器打开 → 必定撞上员工探测 → 必定失败。
我们（以及 `/join` 自助页）能做的只有**别让用户走这条路**。

### 现在的界面改成了这样

**控制台「+ 添加账号」：**

- 主按钮：**「📋 复制登录链接（发到电脑打开）」**
- 二维码下面直接写着：
  > 最稳的方式：把登录链接发到电脑，用电脑浏览器打开，再用手机微信扫电脑屏幕上的二维码
  > 手机上直接在微信里扫这个码，会走到微信内置浏览器 —— 官方登录页在那儿会一直提示「登录失败」，这是微信的限制
- 轮询 20 秒没反应，会自动弹出「复制链接到电脑」的提示
- 扫码成功后服务器**自动拿到账号**，不用回电脑点任何东西（state 是绑在这个链接上的）

**`/join` 自助页：**

- 新增「复制登录链接」按钮
- 文案同步改成「在电脑上登录」，并说明微信内打不开的原因
- **在微信里打开时会自动弹一块黄色提示**（UA 含 `MicroMessenger` 且不含 `wxwork` 才显示）：
  告诉对方「点右上角 ⋯ → 在浏览器打开」，或者「复制链接发到电脑上打开」，
  不会再让人对着一个必然失败的二维码反复扫

### 现在能用的三种加号方式（推荐顺序）

| 顺序 | 方式 | 说明 |
|---|---|---|
| 1️⃣ | 复制登录链接 → 电脑浏览器打开 → 手机微信扫电脑上的码 | 最稳，实测可用 |
| 2️⃣ | 手机「相机」扫码 → 选「在浏览器中打开」 | 绕开了微信内置浏览器，有时能成，不如 ① 稳 |
| 3️⃣ | 手动导入 refreshToken | 见 `手动导入令牌教程.md`，不依赖任何网页 |

## 三、点「清理失效账号」报错（已修）

### 原因

清理接口挂了跨站校验（CSRF 兜底）。老代码是拿 `Host` 头去和浏览器发来的 `Origin` 做**字符串包含**比较：

```python
if host not in origin:   # host = "127.0.0.1:8848"  origin = "https://wb.example.com"
    raise HTTPException(403)
```

走 Nginx 反代时，上游 FastAPI 收到的 `Host` **常常是 `127.0.0.1:8848`**（取决于反代的「发送域名」怎么填），
而浏览器的 `Origin` 是 `https://你的域名` —— 两个永远对不上，于是**合法的清理请求被自己判成跨站，直接 403**。
其他写操作（删账号、改设置）也会中同一个坑，只是清理按钮点得少、先被发现。

### 怎么修的

| 改动 | 位置 | 说明 |
|---|---|---|
| 只比**主机名**，不比整串 | `main.require_same_origin` | `https://a.com:443/x` 和 `a.com` 现在算同一个站 |
| 把 `X-Forwarded-Host` 也算作合法来源 | 同上 | 反代转发了真实域名就能正常校验 |
| 反代只传回环 Host 时放行 | 同上 | `127.0.0.1 / localhost / ::1` 无法与域名比对，放行，CSRF 交给 `SameSite=Lax` 的会话 Cookie 兜底 |
| 清理接口兜异常 | `main.api_cleanup_accounts` | 内部报错回 `{"ok": false, "error": "原因"}`，而不是裸 500 |
| 预览改在本地算 | `static/index.html` | 弹窗直接用已加载的账号列表算「会删几个」，不再依赖 `/api/accounts/expired` |
| 错误按状态码分开提示 | 同上 | 403 / 404·405（服务没重启）/ 数据库忙 / 其他，各给一句人话 |

> 说明：**如果反代只把 `127.0.0.1` 传过来、不传 `X-Forwarded-Host`，程序就无从知道真实域名**，
> 这时只能放行 —— 这是刻意的取舍，安全性由 Cookie 的 `SameSite=Lax`（跨站请求根本不带 Cookie → 401）保证。

### 现在点「清理失效账号」

- 正常情况：直接列出「将清理 N 个账号：xxx、xxx」，确认就删
- 如果服务端还是老版本没重启：提示「服务端版本太旧（当前 x.x.x），请到宝塔重启本服务」，不会再冒一句看不懂的错
- 如果是跨站：提示「被跨站校验拦了（403），请用本站域名打开控制台」

## 四、升级方法

### 宝塔

1. **先备份** `data/` 整个目录（账号凭据都在里面）
2. 上传 `workbuddy-checkin-1.3.1.zip` → 解压覆盖（**不要覆盖 `data/`**）
3. 「Python 项目」→ 重启
4. 右上角版本显示 **1.3.1**

### 命令行

```bash
cd /www/wwwroot/workbuddy-checkin
cp -r data data.bak.$(date +%Y%m%d)
unzip -o ~/workbuddy-checkin-1.3.1.zip -d .
systemctl restart workbuddy-checkin
```

### 升级后要做的两件事

1. **升级当天**：因为老版本可能已经重复领过积分，当天的「今日获得」可能偏高。
   想干净就等第二天，或者手动清一下当天日志：登录控制台 → 日志页可以看到 `[login] 签到成功` 的多条记录。
2. 之前因为这个问题虚高过的数字，**第二天自然就归零了**（「今日获得」只统计当天）。

## 五、兼容性

- **数据库自动迁移**：新增 `checkin_marks` 表，服务启动时自动建，老数据不动
- 老账号不需要重新扫码，升级后第一次登录会补一个标记
- 表只保留最近 60 天，不会一直长
- CSRF 校验改宽后，**原有的「外站请求一律 403」在反代转发真实域名时依然成立**（自检里 6 条用例覆盖）
